# scan_backdoors 2.1: описание параметров

**Это справка по параметрам командной строки (сканер 2.1).** Основной документ —
[README.md](../README.md): там установка, графическая версия 3.0, разметка папок
(`src/`, `assets/`, `data/`) и готовый список заведомо чистых файлов
`data/whitelist-known-clean.txt`. Запуск из корня репозитория:
`python3 src/scan_backdoors.py`, в примерах ниже пути к скриптам указаны так,
как если вы находитесь внутри `src/`.

Сканер бэкдоров, веб-шеллов и вредоносного кода для Joomla/PHP сайтов.
Нужен только Python 3.6+, устанавливать ничего не требуется.

```
python3 scan_backdoors.py [папка] [параметры]
```

Если папка не указана, сканируется текущая. По умолчанию проверяются **все** папки, включая `cache`, `tmp`, `logs`, `media`.

---

## Быстрый старт

```bash
# Обычная проверка: отчёт попадёт в report-data.csv
python3 scan_backdoors.py /home/user/site

# Только самое опасное, за последние 14 дней
python3 scan_backdoors.py /home/user/site --since 14d --only-critical

# Максимально точная проверка: сравнение с чистым Joomla + whitelist
python3 scan_backdoors.py /home/user/site --baseline-dir /tmp/Joomla_5.1.0 --whitelist whitelist.txt
```

## Где инструменты хранят свои данные

Всё, что остаётся между запусками, лежит в **одной** папке: `$SBD_DATA_DIR`, а если она не задана — `~/.scan_backdoors` (на Windows `%USERPROFILE%\.scan_backdoors`). Никогда рядом с кодом и никогда внутри сканируемого сайта.

```
<data>/yarac/                кэш скомпилированных правил .yarac (сканер, --yara-cache)
<data>/whitelist.txt         файл, куда GUI дописывает хеши по «Add to whitelist» (пока не выбран другой)
<data>/joomla-baselines/     эталоны, скачанные joomla_baseline.py (и кнопкой GUI *Fetch baseline*)
<data>/signatures/           установленные релизы правил + ACTIVE + manifest.json + sources.json (updater.py)
<data>/logs/updater.log      что делал апдейтер (ротация, секреты замаскированы)
```

GUI при запуске переносит сюда то, что старые версии держали рядом со сканером (`whitelist.txt`, `joomla-baselines/`), и правит свои настройки; сканер так же переносит кэш правил из временной папки, а `joomla_baseline.py` — кэш из своей папки. Ничего не сливается и не удаляется: если на новом месте что-то уже есть, старое остаётся как есть (утерянный эталон снова скачивается, утерянный кэш пересоздаётся). `SBD_DATA_DIR` можно указать на флешку или временный диск — инструменты кладут туда только свои файлы.

## Параметры

### Что сканировать

| Параметр | По умолчанию | Описание |
|---|---|---|
| `папка` (позиционный) | `.` | Корень сайта. |
| `--max-size МБ` | `5` | Файлы больше указанного размера не читаются. PHP-файл больше лимита не пропускается молча, а помечается как `[ОБФУСКО]`. |
| `--since ДАТА` | выкл. | Проверять только файлы, изменённые позже даты. Формат: `2026-09-01` или `14d` (последние 14 дней). |
| `--exclude-ext СПИСОК` | пусто | Расширения, которые не проверять, через запятую. Точка не обязательна. |
| `--exclude-dir СПИСОК` | пусто | Имена папок, которые не заходить (на любом уровне вложенности). По умолчанию сканируются все. |

```bash
python3 scan_backdoors.py . --max-size 10
python3 scan_backdoors.py . --since 2026-09-01
python3 scan_backdoors.py . --since 7d
python3 scan_backdoors.py . --exclude-ext .js,.json,xml
python3 scan_backdoors.py . --exclude-dir vendor,node_modules
```

> `--since` удобен после взлома: показывает, что изменилось с момента заражения.

### Что искать

| Параметр | Описание |
|---|---|
| `--only-critical` | Искать только `[КРИТИЧЕСКИ]`. Самый быстрый режим, минимум шума. |
| `--no-warnings` | Не искать `[WARNING]` (одиночные `$_POST`, `eval(` и т. п., в чистом Joomla их много). |
| `--min-score N` | Показывать в отчёте только файлы со счётом не ниже `N`. По умолчанию `0`. |

```bash
python3 scan_backdoors.py . --only-critical
python3 scan_backdoors.py . --no-warnings --min-score 10
```

### Отчёты

| Параметр | По умолчанию | Описание |
|---|---|---|
| `--csv ПУТЬ` | `report-data.csv` | CSV-отчёт. Создаётся всегда, если не указан `--no-csv`. |
| `--no-csv` | | Не создавать CSV. |
| `--xlsx ПУТЬ` | выкл. | Дополнительно сохранить отчёт в Excel (листы Files, Hits, Summary). |
| `--json ПУТЬ` | выкл. | Полный отчёт в JSON (для скриптов и автоматизации). |
| `--max-matches N` | `60` | Максимум находок одного уровня на файл в отчёте. Общие счётчики считаются по всем находкам. |

```bash
python3 scan_backdoors.py . --csv /tmp/scan.csv
python3 scan_backdoors.py . --xlsx report.xlsx --json report.json
python3 scan_backdoors.py . --no-csv --json report.json
python3 scan_backdoors.py . --max-matches 20
```

### Снижение ложных срабатываний

| Параметр | Описание |
|---|---|
| `--whitelist ФАЙЛ` | Файл с исключениями (формат ниже). |
| `--audit-whitelisted` | Файлы, попавшие в whitelist по пути/папке/маске, не пропускать: сканировать и показывать только `[КРИТИЧЕСКИ]`. Позиционный (path-based) whitelist по умолчанию вообще не читает содержимое файла; этот флаг — для whitelisted-папок (например, vendor), которые должны молчать обо всём, кроме реального веб-шелла. Выключен по умолчанию. |
| `--baseline-dir ПАПКА` | Папка с **чистым** Joomla той же версии (где лежит `index.php`). Файлы, совпавшие по SHA-256, пропускаются как чистые. Изменённые и лишние файлы в `libraries/`, `includes/`, `administrator/includes/` и в корне помечаются. |

```bash
python3 scan_backdoors.py /home/user/site --baseline-dir /tmp/Joomla_5.1.0
python3 scan_backdoors.py /home/user/site --whitelist whitelist.txt
```

**Формат `whitelist.txt`** (по одной записи в строке, `#` начинает комментарий):

```text
# SHA-256 конкретного файла
5a854ecf8072125e4fabdad558afb7c5fcca486d18107dc8af9d7add60f2c25c

# точный путь от корня сайта
templates/mytpl/helper.php

# вся папка (слэш в конце)
libraries/vendor/

# маска
components/com_k2/*.php
```

Маска никогда не пересекает папки: `components/com_k2/*.php` совпадает с `components/com_k2/x.php`, но не с `components/com_k2/sub/x.php`. Для целой папки используйте форму с завершающим слэшем (`libraries/vendor/`).

### Пользовательские сигнатуры (библиотека)

Сканер может загружать дополнительные сигнатуры из JSON-библиотеки. Графический интерфейс пишет этот файл автоматически (после вашего подтверждения); его можно составить и вручную.

| Параметр | Описание |
|---|---|
| `--user-signatures ФАЙЛ` | Дополнительные сигнатуры из JSON-библиотеки (один массив или объект с массивом `signatures`). Записи валидируются при загрузке: битая запись пропускается с сообщением, никогда не проглатывается молча. Отсутствующий файл останавливает запуск. |

```bash
python3 scan_backdoors.py /home/user/site --user-signatures my-signatures.json
```

**Формат записи** (одна сигнатура на запись):

```json
[
  {"label": "my-webshell", "pattern": "some_literal_or_regex",
   "severity": "critical", "kinds": "php", "weight": 25,
   "flags": "i", "reason": "почему эта сигнатура совпадает"}
]
```

* `label` (2-200 символов; GUI пишет 2-120), `pattern` (валидный регулярное выражение, 2-400 символов, не может совпадать со строкой `""` или `" "`), `severity` (`critical`, `obfuscated` или `warning`), `kinds` (хотя бы один из: `php`, `js`, `html`, `htaccess`, `ini`, `text`, через пробел), `weight` (необязательный, целое число 1-30), `flags` (`i` для безучёта регистра, по умолчанию, если не указан; `none` для учёта), `reason` (необязательный, до 400 символов), `created` (дата ISO, ставится GUI).
* Записи валидируются при загрузке; сканер не падает на битом паттерне.
* GUI пишет подтверждённые предложения в `%USERPROFILE%\.scan_backdoors_user_signatures.json` (записи с одинаковым `label` и `pattern` заменяются, а не дублируются) и передаёт `--user-signatures` следующему скану, когда файл существует и не пуст.

### Правила YARA (необязательный дополнительный движок)

Сканер может дополнительно прогнать правила [YARA](https://github.com/VirusTotal/yara) как ещё один движок детектирования. Это полностью необязательно: без `--yara-rules` ничего не меняется; без установленного пакета `yara-python` сканер сообщит, что движок YARA выключен, и отсканирует встроенными эвристиками ровно как раньше (`pip install -r requirements-optional.txt`).

| Параметр | По умолчанию | Описание |
|---|---|---|
| `--yara-rules ПУТЬ` | | Файл `.yar`/`.yara` или папка с ними (без рекурсии). Каждое срабатывание попадает в отчёт сигнатурой `YARA: <файл>.<правило>`. В `meta` правила можно задать `severity` (critical/high/medium/low/…) и `score` (1-50); правило без meta — всегда `[WARNING]`. Правила могут использовать externals `file_name`, `extension`, `path`, `folder`, `file_size`, `cms`, `wp_root`, `joomla_root`, `rule_language`. Файл правил, который не скомпилировался, — сообщается и пропускается, остальные продолжают работать. Директивы `include` запрещены: каждый файл правил автономен. |
| `--no-yara` | | Никогда не запускать движок YARA, даже с `--yara-rules`. |
| `--yara-cache DIR` | `<данные>/yarac` | Папка кэша скомпилированных `.yarac` (ключ — содержимое правил; битый кэш пересоздаётся автоматически). `<данные>` — `$SBD_DATA_DIR` или `~/.scan_backdoors` (см. [Где инструменты хранят свои данные](#где-инструменты-хранят-свои-данные)); старый кэш во временной папке переносится туда автоматически. |
| `--no-yara-cache` | | Не читать и не писать кэш `.yarac`; компилировать в каждом процессе. |
| `--yara-timeout СЕК` | `5` | Ограничение времени на файл для YARA. Файл, упершийся в лимит, помечается скан-гэпом (`[WARNING]` + строка в STATISTICS), но никогда не считается чистым. |

```bash
python3 scan_backdoors.py /home/user/site --yara-rules /path/to/rules/
```

Смысл скан-гэпа: yara-python молча возвращает неполные совпадения, когда правило упирается в таймаут, поэтому сканер перепроверяет затраченное время сам и помечает любой «упёршийся» файл. В статистике: `YARA: rules loaded / files scanned / scan gaps`.

### Графический интерфейс: AI-ревью

После AI-ревью строка управления вкладки «Запуск и результаты» держит AI-кластер живым:

- счетчик рядом с кнопкой «🤖 AI review» (🤖 threats: N · ⚠ errors: M) — число реальных угроз и число файлов с ошибкой; оба числа показываются, даже если одно из них 0;
- кнопка «🧪 Candidates (K)» — показывает, сколько групп сигнатур можно предложить (файлы с вердиктом 
eal_threat, сгруппированные по сигнатуре);
- отдельная кнопка «🧹 Remove false positives (M)» — доступна в любой момент, не только сразу после ревью; скрывает ложные срабатывания из таблицы, но строки остаются в CSV-отчёте с отметкой AI Handled=false_positive (никогда не удаляются, whitelist не трогается).

Пока выполняется задача или AI выключен, счетчик скрыт и кнопки недоступны.

На широких экранах (от 1100 пикселей) таблица занимает две трети вкладки, а панель «Details / Log» — одну треть в правой колонке (размер меняется перетаскиванием разделителя); на узких экранах раскладка классическая — таблица сверху, панель снизу.

### Интерфейс GUI: внешний вид

GUI полностью перерисован по новому дизайну (cyber-dark по умолчанию): самодостаточный
CSS без внешних шрифтов и CDN (строгая CSP не изменена), логотип издания сохранён в шапке,
тёмная и светлая темы (сохраняются в браузере, учитывают prefers-color-scheme). В шапке —
вкладки «Settings» и «Run and results» с иконками, бейдж соединения с пульсирующей точкой,
круглый переключатель темы (солнце/луна) и кнопка Quit server. Вкладка «Запуск и результаты»:
строка запуска (Start scan с треугольником, Stop с квадратиком, градиентный прогресс-бар,
AI-кластер с кнопкой Candidates и розовым счётчиком) и двухстрочная панель инструментов —
уровневые плашки (All / High / Medium / Low с цветными счётчиками), поиск, фильтр по AI-вердиктам
и Reset в первой строке, действия (Show file / Quarantine / Delete from disk / Mass cleanup /
Select all) во второй; липкий заголовок таблицы 11 px без капса, в начале — колонка чекбоксов (галочка в
шапке выделяет и снимает все видимые строки), колонки фиксированные,
колонка Signature забирает остаток (без горизонтального скролла), уровни — сплошные плашки
(rose HIGH, amber MEDIUM, slate LOW), колонка AI — цветной текст (⚠ threat, ✓ false positive,
? uncertain, ⚠ error, —). Панель Details/Log — снизу на узких экранах (230 px, 6-пиксельный
grip-разделитель с синей подсветкой при наведении), в правой колонке (одна треть, ресайз через
разделитель) на широких (от 1100 пикселей, где таблица занимает две трети). Панель деталей:
полный путь файла с кнопкой Copy, карточки SHA-256 и signature rule (моноширинные, сигнатура
янтарная), коробка вердикта AI, подсвеченная по вердикту (rose/emerald/amber/orange),
скроллируемый блок исходного фрагмента кода. Вкладка «Settings»: четыре карточки в две колонки
(ширина 896 px) — «1. Scan scope & targets», «2. Heuristic scoring & flags», «3. Mass cleanup»,
«4. AI review (local model)» — с цветными заголовками (blue / amber / emerald / indigo),
подписями над моноширинными полями и кнопкой «Go to run →» в шапке. Выпадающий список Reports,
контекстное меню (208 px) и модальные окна следуют макету; тосты — в правом нижнем углу.
Эталон из интерфейса: у поля «Clean Joomla (optional)» на вкладке Settings — кнопка *Fetch baseline*: GUI определяет версию
Joomla сайта по его файлам, спрашивает подтверждение, скачивает официальный Full_Package из релизов `joomla/joomla-cms` по HTTPS
(прогресс — в Log) и сама подставляет папку в настройку. Это единственная часть приложения, выходящая в интернет, и только
после подтверждения. Перед стартом скана GUI сверяет загруженный эталон с версией сайта: при несовпадении (или отсутствии
эталона) предлагает скачать подходящий — скан продолжится автоматически после скачивания — либо, с согласия пользователя,
сканировать без оригиналов (файлы ядра оцениваются только эвристиками, в Log стоит пометка). В подвале — распознанные версии:
Joomla и сторонние движки, публикующие свою версию (VirtueMart и подобные; их оригиналы свободно скачиваются). В панели Details/Log — третья
закладка **Engines**: тот же список таблицей — каждый движок и его версия, отметка загруженного оригинала для ядра Joomla
(✓ загружен, ✗ в папке «Clean Joomla» другая версия, либо не загружено — с путём к папке) и кнопка *Fetch baseline*. Эталон,
скачанный через GUI, ускоряет скан: сканер переиспользует манифест SHA-256, который `joomla_baseline.py` пишет сразу после
скачивания, вместо повторного хеширования тысяч файлов.
AI-ревью следует выделению: с выделенными строками проверяются ровно стоящие за ними файлы —
все, без лимита в 100; без выделения — весь отчёт, как раньше (с лимитом в 100 самых критичных).
Остальное поведение не изменилось: те же JS-id, те же эндпоинты, та же CSP.

### Производительность и вывод

| Параметр | По умолчанию | Описание |
|---|---|---|

| `--strict` | | Код возврата `3` (вместо `0`), если критичных находок нет, но часть файлов не удалось прочитать: скан неполный, «чисто» не доказано. Для CI/cron. |
| `--no-progress` | | Не показывать индикатор прогресса. |
| `--progress-lines` | | Машиночитаемые строки `@@PROGRESS`, `@@FILE`, `@@STATS`, `@@DONE` в вывод. Нужен для графической оболочки (прогресс-бар, кнопки отчётов), работает и без терминала. |
| `--version` | | Показать версию. |
| `-h`, `--help` | | Справка по параметрам. |

```bash
python3 scan_backdoors.py . --workers 1
python3 scan_backdoors.py . --workers 4 --no-progress
```

## Колонки CSV-отчёта

| Колонка | Значение |
|---|---|
| Score | Балл файла (чем выше, тем опаснее). Отчёт отсортирован по убыванию. |
| Verdict | `HIGH`, `MEDIUM` или `LOW`. |
| Severity | `[КРИТИЧЕСКИ]`, `[ОБФУСКО]` или `[WARNING]`. |
| File | Путь файла от корня сайта. |
| Line | Номер строки (пусто для находок по имени, расположению или бинарному содержимому). |
| Signature | Название сработавшей сигнатуры. |
| Snippet | Фрагмент кода с находкой. |
| Size | Размер в байтах. |
| Modified | Дата изменения файла. |
| Удалить | Ваша пометка. По умолчанию везде `Нет`, меняйте на `Да` после разбора. |
| SHA-256 | Хэш файла (для whitelist и проверки в онлайн-базах). |
| AI Verdict | Вердикт AI-ревью: `real_threat`, `false_positive`, `uncertain` или `error`. Пишет только GUI; сканер сам этот столбец не трогает. |
| AI Comment | Комментарий AI-ревью к файлу. |
| AI Handled | Пометка GUI: `false_positive` — файлы скрыты из таблицы (строки остаются в CSV). Не удалять записи вручную. |

## Уровни и баллы

**Серьёзность находки**

| Уровень | Что означает | Баллы по умолчанию |
|---|---|---|
| `[КРИТИЧЕСКИ]` | Почти наверняка вредонос: eval от `$_POST`, имена известных шеллов, PHP в картинке, `auto_prepend_file`. | 10 (явные признаки: 15 до 30) |
| `[ОБФУСКО]` | Цепочки декодирования, подозрительные имена, длинные строки, высокая энтропия. | 3 |
| `[WARNING]` | Одиночные примитивы (`$_GET`, `exec(`). В чистом Joomla встречаются часто. | 1 |

**Вердикт файла:** `HIGH` при счёте от 25, `MEDIUM` от 10, иначе `LOW`.

Что скрипт проверяет дополнительно:
- PHP-код внутри картинок, шрифтов и CSS;
- двойные расширения (`image.php.jpg`) и бэкапы (`.php.bak`, `.suspected`);
- PHP в `images/` и `tmp/`;
- лишний код в `configuration.php` после `class JConfig`;
- опасные правила в `.htaccess` (`auto_prepend_file`, `AddType` для картинок, клоакинг по User-Agent и Referer).

## Коды возврата

| Код | Значение |
|---|---|
| `0` | Критичных находок нет |
| `2` | Есть `[КРИТИЧЕСКИ]` |
| `3` | С `--strict`: критичных находок нет, но часть файлов не удалось прочитать (скан неполный) |
| `1` | Ошибка запуска (папка не найдена, неверный формат параметра) |

Пример для автоматизации (cron, CI):

```bash
python3 scan_backdoors.py /home/user/site --only-critical --no-csv --json /tmp/scan.json
if [ $? -eq 2 ]; then echo "Найдены критичные файлы!" | mail -s "Alert" admin@example.com; fi
```

## Рекомендуемый порядок работы

1. Получить чистый Joomla той же версии: `python3 joomla_baseline.py 5.1.0 --out /tmp/baselines` (скрипт сам скачает, проверит и распакует; ручной вариант — скачать и распаковать, например, в `/tmp/Joomla_clean`).
2. Запустить полный скан: `python3 scan_backdoors.py /home/user/site --baseline-dir /tmp/Joomla_clean`.
3. Открыть `report-data.csv`, сначала разобрать `HIGH`.
4. Легальные файлы сторонних расширений добавить в `whitelist.txt`.
5. Заражённые файлы удалить или восстановить из чистой копии, в колонке «Удалить» отметить `Да`.
6. Повторить скан, пока критичных находок не останется, и сменить пароли (админка, FTP, база).
7. Позже запускать регулярно: `--since 7d --only-critical`.

# clean_malware.py: массовая очистка

Рекурсивно находит и убирает **заведомо вредоносные** файлы известных семейств. Работает по содержимому, а не только по имени. Тех, у кого имя из списка, но сигнатур нет, показывает для ручной проверки и не трогает.

```
python3 clean_malware.py /путь/к/сайту                  # 1. пробный запуск: ничего не меняется
python3 clean_malware.py /путь/к/сайту --apply          # 2. перенос в карантин (можно откатить)
python3 clean_malware.py --restore /путь/_quarantine_.../manifest.json   # откат
python3 clean_malware.py /путь/к/сайту --apply --delete # удалить безвозвратно
```

| Параметр | По умолчанию | Описание |
|---|---|---|
| `папка` | `.` | Корень сайта. Корень диска отклоняется. |
| `--apply` | выкл. | Без него только план. |
| `--delete` | выкл. | Удалять безвозвратно, без карантина. |
| `--families` | `htaccess,backdoor` | `htaccess` (замки `.htaccess`), `backdoor` (метка `BiaoJiOk`, goto/eval-загрузчики, крошечный `index.php` с `include base64_decode("…")` и его payload в `.flv`/картинке), `filemanager` (веб-файловые менеджеры без авторизации, как `elp.php`). |
| `--htaccess-mode` | `clean` | `clean`: вырезать только вредоносные блоки, легальные правила сохранить (если ничего не осталось, файл удаляется). `delete`: удалять файл целиком. |
| `--quarantine-dir` | рядом с сайтом | Куда класть копии. Должен быть вне папки сайта. |
| `--exclude-dir` | пусто | Имена папок, которые не трогать. |
| `--whitelist` | выкл. | Тот же формат, что у сканера: SHA-256, пути, папки (`/` в конце), маски `*`. |
| `--report` | `cleanup-report.csv` | CSV: статус, семейство, действие, файл, размер, хэш, ошибка. |
| `--restore MANIFEST` | | Вернуть файлы из карантина. Для очищенных `.htaccess` восстанавливает исходное содержимое. Манифест не доверяется слепо: файл восстанавливается только внутри папки сайта, записанной в манифесте, и только если карантинная копия всё ещё совпадает с записанным SHA-256. Подделанный манифест или подменённая копия отклоняются (`[REFUSED]`, код `2`). |
| `--replace-core` | выкл. | Заменять изменённые файлы ядра Joomla оригиналами из `--baseline-dir`. Нужен `--apply` для выполнения. Изменённый файл сохраняется в карантин (`*.modified`), оригинал пишется поверх на месте (владелец и права сохраняются), хэш проверяется после записи. |
| `--baseline-dir` | | Папка с чистым полным дистрибутивом Joomla **той же версии** (там лежит `index.php`). |
| `--core-ext` | `.php,.js,.html,.htm` | Расширения, которые заменяются. Языковые `.ini` по умолчанию не трогаются (их правят переводчики). |
| `--max-modified-percent` | `30` | Если «изменено» больше N% файлов ядра, замена отменяется: скорее всего, эталон не той версии. |
| `--force-version` | выкл. | Пропустить проверки версии и процента (**опасно**). |
| `--no-media` | выкл. | Не проверять картинки/видео на PHP-код внутри (быстрее на больших сайтах). По умолчанию проверяются `.jpg .png .gif .ico .flv .mp3 .mp4` и др. |
| `--progress-lines` | | Служебные строки `@@...` для GUI. |

**Как работает безопасно:** карантин с проверкой хэша перед удалением; файлы с правами 0444 и каталоги 0555 обрабатываются (права каталога возвращаются); символические ссылки пропускаются; повторный запуск ничего не находит.

Коды возврата: `0` успех, `1` ошибка запуска (в том числе несовпадение версии эталона), `2` часть файлов обработать не удалось либо запись `--restore` отклонена.

**Замена файлов ядра (пример):**
```
python3 clean_malware.py /путь/к/сайту --replace-core --baseline-dir /tmp/Joomla_5.1.2        # план
python3 clean_malware.py /путь/к/сайту --replace-core --baseline-dir /tmp/Joomla_5.1.2 --apply  # выполнить
```
Защиты: версии сайта и эталона должны совпадать (иначе отказ); если изменено больше 30% файлов, замена отменяется; файлы, которых нет в эталоне (расширения, шаблоны, `configuration.php`), не трогаются; файлы из `--whitelist` (ваши правки ядра) не заменяются. Лишние файлы в `libraries/`, `includes/`, `administrator/includes/` (нет в эталоне) только выводятся списком для ручной проверки. Откат: `--restore .../manifest.json`.

**В GUI:** кнопка «🧹 Массовая очистка» на вкладке результатов. Сначала пробный прогон с цифрами, потом подтверждение, потом очистка. Режим (карантин или безвозвратно), семейство `filemanager` и галочка «Заменять изменённые файлы ядра оригиналами» (берёт папку «Чистая Joomla» из настроек) задаются на вкладке «Настройки». `clean_malware.py` должен лежать рядом со сканером.

# joomla_baseline.py: чистый эталон Joomla

Скачивает официальный полный дистрибутив Joomla (Full_Package) нужной версии из релизов `joomla/joomla-cms`, проверяет его и распаковывает в локальный кэш с манифестом SHA-256 по каждому файлу. Результат передаётся в `--baseline-dir` сканеру или очистителю — вручную чистый дистрибутив скачивать, распаковывать и сверять не нужно.

```
python3 joomla_baseline.py 3.9.27
    joomla-baselines/Joomla_3.9.27/                <- передаётся как --baseline-dir
    joomla-baselines/Joomla_3.9.27.baseline.json   <- манифест: каждый файл и его SHA-256
```

| Параметр | По умолчанию | Описание |
|---|---|---|
| `версия` (позиционный) | — | Точная стабильная версия, например `3.9.27` (иначе «Invalid version»). |
| `--out ПАПКА` | `<данные>/joomla-baselines` | Куда класть кэш (внутри [папки данных](#где-инструменты-хранят-свои-данные); кэш, оставшийся рядом со скриптом, один раз переносится туда). |
| `--force` | выкл. | Перескачать, даже если кэш валиден. |
| `--keep-archive` | выкл. | Оставить скачанный zip (по умолчанию удаляется после распаковки). |
| `--version` | | Показать версию. |
| `-h`, `--help` | | Справка. |

**Быстрые хеши для сканера:** сканер с `--baseline-dir` на скачанную папку берёт хеши из манифеста, не пересчитывая тысячи файлов (файлы, которых в манифесте нет, хешируются на месте — правленный вручную эталон не сможет выдать изменённое ядро за чистое).

**Целостность, два уровня:** если API GitHub публикует официальный SHA-256 артефакта — сверка обязательная, при несовпадении отказ (артефакт удаляется). Для старых релизов, где дайджест не публикуется, распакованный дистрибутив должен сам отчитываться о запрошенной версии, иначе отказ. Повторный запуск проверяет кэш офлайн по манифесту и скачивает заново только если какой-то файл изменился или манифест утерян.

Коды возврата: `0` — успех (скачано и проверено, либо кэш валиден), `1` — ошибка (версия, API GitHub, дайджест, версия дистрибутива, заблокированный файл).

**Пример связки с очистителем:**

```
python3 joomla_baseline.py 3.9.27 --out /tmp/baselines
python3 clean_malware.py /путь/к/сайту --replace-core --baseline-dir /tmp/baselines/Joomla_3.9.27 --apply
```

# updater.py: обновление сигнатур

`updater.py` устанавливает пакеты правил YARA для [движка YARA](#правила-yara-необязательный-дополнительный-движок), чтобы набор правил мог расти между релизами самой утилиты. Он намеренно консервативен: набор правил становится активным только целиком, только после проверок целостности и компиляции, а предыдущий релиз всегда остаётся на диске для отката. Ничего скачанное не исполняется — файлы правил только компилируются `yara-python` в отдельном подпроцессе с таймаутом.

```
python3 updater.py --update-signatures              # пакет самого проекта (адрес закреплён в sources.json)
python3 updater.py --update-from-bundle sigs.zip    # офлайн: пакет, который вы достали сами
python3 updater.py --update-from-upstream           # синхронизация апстримов, закреплённых по коммиту
python3 updater.py --status                         # что активно сейчас (JSON)
python3 updater.py --rules-path                     # папка правил для --yara-rules
python3 updater.py --rollback-signatures            # вернуть предыдущий релиз
```

| Параметр | Описание |
|---|---|
| `--update-signatures` | установить пакет самого проекта: URL и SHA-256 архива закреплены в `sources.json`, только HTTPS и только хосты из списка |
| `--update-from-bundle ФАЙЛ` | установить пакет из локального zip (офлайн-путь; все проверки на месте) |
| `--update-from-upstream` | подтянуть апстримы из `sources.json`: синхронизируются только закрепленные по полному 40-символьному SHA коммита **и** по закреплённому SHA-256 архива — ссылка на ветку отклоняется до любого запроса. Упавший источник сохраняет правила, которые он внёс в предыдущий релиз (падающий источник не затирает остальные), код возврата `3` (частично) |
| `--rollback-signatures` | сделать активным предыдущий релиз |
| `--status` | напечатать JSON: активный релиз, число правил, проверка, упавшие источники |
| `--rules-path` | напечатать папку `rules` активного релиза (код `1`, если ничего не установлено) — то, что передают в `scan_backdoors.py --yara-rules` |
| `--package-sha256 HEX` | внешний SHA-256 архива: с ним обновление считается **проверенным**; без него апдейтер отказывает |
| `--allow-unverified` | принять пакет, который нечем проверить, — громко, и в манифест пишется `"verified": false` |
| `--only ИМЯ` | с `--update-from-upstream`: синхронизировать только этот источник (остальные переносятся из прошлого релиза) |
| `--data-dir ПАПКА` | папка данных (по умолчанию `%SBD_DATA_DIR%`, иначе `~/.scan_backdoors`) |
| `--version` | версия комплекта |

**Что делает одно обновление**: скачивание (потоково, с жёстким лимитом размера) → сверка закреплённого SHA-256 → безопасная распаковка (только `.yar`/`.yara` и файлы лицензий; защита от zip-slip, симлинков и «бум»; наружу из staging-папки ничего не пишется) → компиляция каждого файла правил в отдельном подпроцессе с таймаутом (`engines/yara_check.py`) → атомарное перемещение релиза на место → переключение указателя `ACTIVE` → перезапись манифеста. Любой сбой на любом шаге оставляет активным предыдущий релиз.

**Модель доверия**: обновлению доверяем, только если SHA-256 архива закреплён (в `sources.json` или передан `--package-sha256`). Манифест самого пакета обязан объявлять каждый файл правил с его SHA-256 — необъявленное правило отклоняет весь пакет. Подпись пакета (`minisign`/`cosign`) пока не реализована: до этого «проверено» означает «совпало с закреплённым хешем», а `--allow-unverified` — явный и записываемый в лог выход.

**Где всё лежит** (внутри `--data-dir`, создаётся при первом запуске):

```
signatures/ACTIVE                  имя активного релиза (одна строка)
signatures/manifest.json           что активно, что установлено, что упало
signatures/sources.json            закреплённые каналы (править только руками)
signatures/releases/<имя>/rules/   файлы правил каждого релиза
logs/updater.log                   ротируемый лог (токены и секреты маскируются)
```

`sources.json` создаётся как шаблон: `package_source` (пакет самого проекта: `url` + `sha256`) и `upstream` (список `{name, repo, commit, archive_sha256, license}`). Закреплять хеши и сторонние лицензии должен человек после проверки — см. `docs/OPEN_QUESTIONS.md`. Правила апстримов — сторонний контент: лицензию нужно прочитать до закрепления; апдейтер записывает `license`, но не оценивает её.

**Как пользоваться установленными правилами**: `python3 src/scan_backdoors.py /home/user/site --yara-rules "$(python3 src/updater.py --rules-path)"`. GUI делает это сам: когда релиз установлен, сканирование получает его папку правил (путь выбирает сервер, страница в браузере повлиять не может), а на вкладке **Engines** показан активный пакет с кнопками *Update signatures* и *Roll back*.

**Для проверки компиляции нужен `yara-python`** (`pip install yara-python`): без него апдейтер отказывается активировать набор, который не может проверить компиляцией. Коды возврата: `0` — всё обновлено, `1` — ошибка запуска/настройки, `3` — ЧАСТИЧНО (хотя бы один источник упал — см. манифест), `4` — сбой проверки или сети (активным остаётся предыдущий релиз).
