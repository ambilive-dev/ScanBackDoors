# OPEN QUESTIONS — открытые вопросы ТЗ v2

Открытые пункты дорожной карты. Каждый закрывается отдельным решением владельца
или подтверждением по первоисточнику; в код не переносится, пока не закрыт.

## Спринт 0 (внешние зависимости приёмки)

1. **Корпус чистых CMS для FP-бюджета.** Сейчас baseline — только синтетическая
   фикстура (28 файлов, 0 находок, `tests/golden/fp_baseline_synthetic.json`).
   Для реального бюджета нужны: выбор 1–2 чистых установок Joomla/WP + популярных
   расширений (PHPMailer, phpseclib — они уже дают ложные срабатывания на сторонних
   YARA-правилах), источник загрузки, лицензии, способ фиксации в CI (скачивание по
   hash в кэш, не коммит кода CMS). Решение владельца: брать/не брать, объём.
2. **Python 3.6.** README и докстринги обещают 3.6+, CI тестирует 3.8/3.11/3.13,
   совместимость статическая (`tests/test_compat.py`). Оставить обещание (CI-джоб с
   `python:3.6` рантаймом)? Или понизить обещание до 3.8 — это изменение публичного
   контракта, только решение владельца.
3. **Каталог данных.** Два места пишут «рядом со сканером»: `<папка сканера>/whitelist.txt`
   (дефолт GUI-дописывания whitelist) и `<папка сканера>/joomla-baselines/` (Fetch
   baseline). ТЗ требует каталог данных вне сайта/правил — переносить ли в
   `~/.scan_backdoors/...` и нужна ли миграция существующих установок? Пока безопасно
   (не внутри сканируемого сайта), но смешивает код и данные.
   Спринт 1 добавил третье место: кэш `.yarac` — временно в `%TEMP%/scan-backdoors-yarac`
   (`--yara-cache` перебивает); переедет вместе с решением по этому пункту.
   **Спринт 2 (решение по умолчанию, пересматривается этим пунктом):** новые данные
   апдейтера уже лежат вне кода — `$SBD_DATA_DIR` или `~/.scan_backdoors/`
   (`signatures/{releases,ACTIVE,manifest.json,sources.json}` + `logs/updater.log`);
   GUI читает тот же корень.
   **ЗАКРЫТО (решение владельца: жёсткий переезд + авто-перенос).** Единый корень —
   `$SBD_DATA_DIR`, иначе `~/.scan_backdoors` (на Windows `%USERPROFILE%\.scan_backdoors`),
   иначе (дома нет) `%TEMP%/scan-backdoors`: `yarac/`, `whitelist.txt`,
   `joomla-baselines/`, `signatures/`, `logs/`. Старые места не читаются — они один раз
   ПЕРЕНОСЯТСЯ: GUI при старте (`migrate_data_locations`, заодно правит настройки
   `whitelist_path`/`baseline_dir`), сканер перед первым YARA-сканом
   (`migrate_yarac_cache`), `joomla_baseline.py` при запуске
   (`migrate_legacy_baselines`). Не сливает и не удаляет: если на новом месте уже есть —
   старое остаётся как есть (эталон докачивается, кэш пересобирается). Флаги
   `--yara-cache`/`--out` перебивают расположение как раньше; форма флагов не менялась.
   Тесты: `tests/test_data_paths.py`.
4. **Ветка/теги рабочего процесса.** Владелец пушит в `main` напрямую; ТЗ просит
   не изобретать git-flow. Подтверждение: спринты коммитим в `main` последовательными
   коммитами, релиз — отдельный коммит + тег (как v3.3/v3.3.1)?

## Внешние источники (все [ПРОВЕРИТЬ] из ТЗ, закрывать перед соответствующим спринтом)

5. **YARA**: availability wheels `yara-python` для 3.8–3.13 (Windows CI!), поведение
   `timeout` (инструкция, не прерываемый оверран?), YARA-X как альтернатива. Решение
   принималось бы в Спринте 1 — гонять ли его вообще.
   **ЗАКРЫТО в Спринте 1 (проверено на yara-python 4.5.4, локально):**
   движок сделан опциональным (`requirements-optional.txt`); биначные wheels для
   CPython 3.8–3.13 Windows/macOS/Linux существуют на PyPI (`yara-python` 4.5.x —
   [ПРОВЕРИТЬ] в CI на всех нодах матрицы при добавлении опционального прогона).
   `match(timeout=N)` при истечении НЕ бросает `TimeoutError` и НЕ возвращает флаг —
   молча возвращает Неполные совпадения (зафиксировано экспериментально); поэтому
   движок сам измеряет wall-clock и помечает «упёршийся» файл scan-gap'ом.
   `externals` привязываются значением на каждый `match()` (типы — плейхолдерами при
   компиляции), `include` резолвится по умолчанию → заблокирован `include_callback`
   + pre-scan. YARA-X как альтернатива — отдельный вопрос на будущее (другой API).
6. **Лицензии сторонних правил** (Neo23x0/signature-base и др.) — специфичны,
   вендоринг запрещён ТЗ; для `--update-from-upstream` обязателен ревью.
7. **abuse.ch MalwareBazaar** — актуальный Auth-Key-механизм, форматы выгрузок,
   пригодность PHP/JS-подмножества. Не входит в MVP.
8. **NVD API 2.0 / годовые фиды** — схемы, квоты, `.meta`-дайджесты; полный CPE для
   joomla/wordpress (экранирование `joomla\!` в CPE dictionary — проверить).
9. **WPVulnerability.net** — доступность, схемы `/plugin/{slug}/`, `/theme/{slug}/`,
   `/core/<version>/`, `/plugin/<slug>/`, `/theme/<slug>/` (OpenAPI:
   `docs.wpvulnerability.com/openapi.yaml`); рабочим хостом взят `api.wpvulnerability.com`
   (в документации встречается и `www.wpvulnerability.net`); конверт `{error, message, data,
   updated}` - 200 c `error:1` на неизвестном пути, 403 на плохой ключ, 503 на перегрузке;
   у core-записей поля `operator` нет (версии уже отфильтрованы сервером), у plugin/theme оно
   есть как `{min_version, min_operator, max_version, max_operator, unfixed}` с операторами PHP
   `version_compare`; KEV лежит в `impact.ssvc.kev`, серьёзность в `impact.cvss3.severity`,
   `impact` иногда приходит пустым списком; неизвестный slug - `error:0, data.vulnerability:
   null`. Открыто: условия использования и лимиты (перед тем, как включать `--online` по
   умолчанию).
10. **WordPress checksums API** (`api.wordpress.org/core/checksums/1.0/`) — параметры,
    алгоритм (md5?), покрытие версий. Кандидат Спринта 3.
     **Закрыто (Спринт 3, 2026-11-28):** `?version=<v>&locale=<loc>` → `{"checksums":
     {путь: md5}}` (2960 файлов для 6.4.2); без `locale` ответы лежат под ключом версии;
     неизвестная или мусорная версия → `{"checksums": []}` - пустой **список**, а не объект
     (на это опирается тест-ловушка); `4.9.6` доступен. Отдельного checksums-API для плагинов
     и тем нет: `/plugins/checksums/` и `/themes/checksums/` отдают 404, поэтому у компонентов
     эталонного файла нет, и в отчёте это сказано прямо. MD5 здесь - ключ каталога, а не
     подпись подлинности: ответ на вопрос «совпадает ли файл с опубликованным wordpress.org»,
     и ничего больше.
11. **CISA KEV** — актуальный JSON-URL. **Не использован в Спринте 3:** KEV приходит из
   `impact.ssvc.kev` ответов WPVulnerability и из поля `kev` локальной базы; отдельный фид
   CISA не опрашивается (это ещё один хост и ещё одно разрешение владельца).
12. **Joomla VEL** (vel.joomla.org) — есть ли машиночитаемая выгрузка и условия.
   **Открыто (перенесено за рамки Спринта 3):** фид не проверен, поэтому аудит Joomla
   работает только по локальной базе: `--online` для Joomla-расширений ни о чём не спрашивает,
   и в отчёте это написано. `engines/cms_api.py` не содержит для этого ни одного URL.
13. **Подпись пакета сигнатур** — модель ключа/ротации/доставки публичного ключа;
    пока не определена, канал `--update-signatures` не запускаем.
    **Статус Спринта 2:** канал реализован (URL+sha256 из `sources.json`), но сам
    публичный пакет и публикации релизов не созданы — канал возвращает явную ошибку
    «не сконфигурирован».
    **Спринт 2.5 (решение владельца: minisign + опциональная `cryptography`):**
    проверка подписи реализована в `updater.py` в формате minisign (Ed25519: `Ed` —
    подпись по файлу, `ED` — по BLAKE2b-512 файла); ключ закрепляется в `sources.json`
    (`package_source.minisign_pub` / `minisign_pub_file` / `minisign_pub` у апстрима),
    подпись ищется по `<url>.minisig` или `signature_url`; сверяется key id, проверяются
    и подпись файла, и глобальная подпись; несовпавшая подпись — отказ, а не откат к
    хешу. `--signature ФАЙЛ` — то же для офлайн `--update-from-bundle`;
    `--require-signature` запрещает откат к закреплённому SHA-256. Без `cryptography`
    апдейтер честно работает по хешу и пишет `"signature": "not-checked"`. Формат
    проверен тестами по подписям настоящего minisign (фикстуры из эталонного порта
    jedisct1/go-minisign, ISC); сам бинарь minisign не запускается и не требуется.
    Осталось решение владельца по публикации: (а) где лежит секретный ключ и кто им
    подписывает (`minisign -G`, офлайн-машина); (б) где публикуются `rules.zip` +
    `rules.zip.minisig` (релиз на GitHub?); (в) как публичный ключ попадает в
    `sources.json` установки — пока только руками; (г) ротация и отзыв ключа. Пока
    (а)–(в) не решены, `package_source` остаётся пустым, и канал по умолчанию закрыт.
    [ПРОВЕРИТЬ] сквозную совместимость своим бинарём: `minisign -V -m rules.zip -x
    rules.zip.minisig -p <ключ>` должен принимать те же пары, что и `updater.py`.

16. **Чем наполнять локальную базу уязвимостей.** `--audit-cve` без `--online` судит только
    по `audit/vulnerabilities.json` (schema 2), а она поставляется пустой: выдумывать CVE
    сканер не имеет права, и честный офлайн-аудит сейчас говорит «0 записей». Нужен
    конвейер-поставщик: из какого источника (WPVulnerability API, CISA KEV, advisory-архивы
    WP), с какой частотой, под какой лицензией и где физически лежит файл
    обновления (тот же `sources.json`-канал, что и правила YARA, или отдельный `--update-audit`).
    Пока его нет, `--online` обязателен для осмысленного аудита, и это разрешено только
    явным флагом. [ПРОВЕРИТЬ] условия перераспространения выбранных источников.
