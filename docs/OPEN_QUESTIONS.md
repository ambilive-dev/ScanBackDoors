# OPEN QUESTIONS — открытые вопросы ТЗ v2

Открытые пункты дорожной карты. Каждый закрывается отдельным решением владельца
или подтверждением по первоисточнику; в код не переносится, пока не закрыт.

## Спринт 0 (внешние зависимости приёмки)

1. **Корпус чистых CMS для FP-бюджета.** Сейчас baseline — только синтетическая
   фикстура (28 файлов, 0 находок, `tests/golden/fp_baseline_synthetic.json`).
   Для реального бюджета нужны: выбор 1–2 чистых установок Joomla/WP + популярных
   расширений (PHPMailer, phpseclib — они уже дают ложные срабатывания на сторонних
   YARA-правилах), источник загрузки, лицензии, способ фиксации в CI (скачивание по
   hash в кэш, не коммит кода CMS). Решение владельца: брать/не брать, объём.
2. **Python 3.6.** README и докстринги обещают 3.6+, CI тестирует 3.8/3.11/3.13,
   совместимость статическая (`tests/test_compat.py`). Оставить обещание (CI-джоб с
   `python:3.6` рантаймом)? Или понизить обещание до 3.8 — это изменение публичного
   контракта, только решение владельца.
3. **Каталог данных.** Два места пишут «рядом со сканером»: `<папка сканера>/whitelist.txt`
   (дефолт GUI-дописывания whitelist) и `<папка сканера>/joomla-baselines/` (Fetch
   baseline). ТЗ требует каталог данных вне сайта/правил — переносить ли в
   `~/.scan_backdoors/...` и нужна ли миграция существующих установок? Пока безопасно
   (не внутри сканируемого сайта), но смешивает код и данные.
4. **Ветка/теги рабочего процесса.** Владелец пушит в `main` напрямую; ТЗ просит
   не изобретать git-flow. Подтверждение: спринты коммитим в `main` последовательными
   коммитами, релиз — отдельный коммит + тег (как v3.3/v3.3.1)?

## Внешние источники (все [ПРОВЕРИТЬ] из ТЗ, закрывать перед соответствующим спринтом)

5. **YARA**: availability wheels `yara-python` для 3.8–3.13 (Windows CI!), поведение
   `timeout` (инструкция, не прерываемый оверран?), YARA-X как альтернатива. Решение
   принималось бы в Спринте 1 — гонять ли его вообще.
6. **Лицензии сторонних правил** (Neo23x0/signature-base и др.) — специфичны,
   вендоринг запрещён ТЗ; для `--update-from-upstream` обязателен ревью.
7. **abuse.ch MalwareBazaar** — актуальный Auth-Key-механизм, форматы выгрузок,
   пригодность PHP/JS-подмножества. Не входит в MVP.
8. **NVD API 2.0 / годовые фиды** — схемы, квоты, `.meta`-дайджесты; полный CPE для
   joomla/wordpress (экранирование `joomla\!` в CPE dictionary — проверить).
9. **WPVulnerability.net** — доступность, схемы `/plugin/{slug}/`, `/theme/{slug}/`,
   условия использования.
10. **WordPress checksums API** (`api.wordpress.org/core/checksums/1.0/`) — параметры,
    алгоритм (md5?), покрытие версий. Кандидат Спринта 3.
11. **CISA KEV** — актуальный JSON-URL.
12. **Joomla VEL** (vel.joomla.org) — есть ли машиночитаемая выгрузка и условия.
13. **Подпись пакета сигнатур** — модель ключа/ротации/доставки публичного ключа;
    пока не определена, канал `--update-signatures` не запускаем.

## Мелочи, найденные разведкой

14. `DEFAULT_MAX_SIZE` в сканере — мёртвая константа (реальный лимит `--max-size`).
    Удалить или использовать? Мелочь, трогать в Спринте 0 не стали (запрет на
    поведенческие правки до страховочной сетки; удаление безопасно только вместе с
    полным grep — сделать при первом же случае).
15. Самоскан репозитория находит собственные `.pyc` (в кэшах Python лежат строки
    сигнатур сканера) — при CI self-scan (ТЗ §9.2) исключать `__pycache__` наравне с
    правилами/тестами.
